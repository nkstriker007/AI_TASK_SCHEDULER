# Decision log

D1–D14 and D16 are recorded in the design doc (section 14). This file records the decisions made during the build. D27–D30 were added with the `planner/` worker (14 Oct) and renumbered from D20–D23 so they do not collide with Person B's Day 2 entries.

| ID | Decision | Rationale |
|---|---|---|
| D15 | **Research data source: LLM-only knowledge**  Research executors answer from model knowledge; web search is not used. | Groq has no built-in web-search tool on the structured-output models, so search would need a separate provider and API key. LLM-only keeps cost and rate limits predictable for E7. Report results as "model knowledge as of training cutoff", not as current facts. Revisit if E7 answers are too stale. |
| D17 | **LLM provider: Groq** (`groq` Python SDK, `GROQ_API_KEY`). Planner default model `openai/gpt-oss-120b`, overridable with `ATS_PLANNER_MODEL`. | Team choice. `gpt-oss-120b` supports Groq's strict `json_schema` mode, which guarantees the plan's shape. |
| D18 | **Strict-mode schema is a relaxed copy.** `llm.LLM_PLAN_SCHEMA` makes every field required and nullable (Groq strict rules), leaves out length/pattern/count limits and `sim_subplan`, and the output is normalized (nulls dropped) and then run through the full validator. | Strict mode doesn't guarantee the finer constraints. The validator stays the only judge of validity (design doc 4.4). A test checks the LLM schema against the strict rules. |
| D19 | **Plan-level extensions frozen with contract #1:** `hints.expected_fanout`, `hints.sim_subplan`, and the `Subplan`/`SubplanTask` models (local IDs `s1…`, no nested expand, ≤ 20 tasks). | The design doc's Day 1 joint hour includes the expand type and subplan model, and freezing them now avoids a contract change on Day 6. See `docs/contract.md`. |
| D20 | **Scheduling policy is a separate object behind `SchedulingPolicy { push; pop; }`.** `ExecutionState` decides *what* is ready; the policy decides *which* ready task goes first. `FifoPolicy` is the baseline. `CriticalPathPolicy` (largest bottom level first, ties to the earlier task in plan order) was built on Day 2, ahead of the Day 4 plan. Policies are chosen by name (`fifo`, `critical-path`). | Keeps the state machine free of policy (design doc 3.2, D14), so E4 can compare policies without touching the core. Building critical-path early cost little once `Analysis` computed bottom levels, and gives the simulator a second policy to test against. |
| D21 | **Simulator semantics.** Discrete-event, virtual time. A task's duration is its `estimated_seconds` hint, otherwise `--default-seconds` (10). Jitter multiplies each attempt by a factor in [1−j, 1+j] derived from (seed, task, attempt), so a run is deterministic for a given seed regardless of dispatch order. Simultaneous completions are processed in task order, then free workers are filled immediately. `--fail` makes a task fail permanently; `--flaky` makes it fail on attempt 1 and succeed on retry. | Determinism makes the simulator the reference for E1 and lets invariant tests compare exact numbers (design doc D7, 7.4). Flaky injection exercises the RETRYING path in `ExecutionState` before Redis exists. |
| D22 | **Metric definitions in the simulator.** Sequential time = sum of every task's first-attempt duration. Speedup = sequential / makespan, reported as 0 when the run failed; max speedup = sequential / critical path. Utilization = worker-seconds actually used, *including failed attempts*, / (workers × makespan); with unlimited workers, peak parallelism stands in for the worker count. | Follows design doc 3.10, with two clarifications it left open: failed attempts still occupy a worker, so they count toward utilization; and "workers" is undefined when unlimited. A speedup for a failed run would be meaningless. |
| D23 | **`ats_sim` exit codes: 0 every task completed, 1 invalid plan or invalid arguments, 2 execution failed.** `--json` prints the full report, or `{"valid": false, "issues": [...]}` for an invalid plan. | Same convention as the planner CLI and design doc 7.5, so scripts and `tests/test_parity.py` can tell "plan rejected" (1) from "plan ran but a task failed" (2). |
| D24 | **Worker acknowledges a message only after its event is on `task:events`.** Unclassified executor exceptions are reported as `retryable` (atsd's max attempts bounds them). A message that violates contract #2 is reported as a `permanent` failure if its `attempt_id` is readable, then acknowledged. A task whose input result is missing fails `permanent`. | A crash before the event leaves the entry pending, which is safe because atsd's deadline owns recovery (D10); the worker never claims other consumers' entries. Retrying an unknown bug a bounded number of times is cheaper than failing a request on one transient library error. A missing input means atsd dispatched too early, which retrying wouldn't fix. |
| D25 | **Request intake and status format** (`requests:new` carries the plan file; the API writes `plan:<id>`; atsd writes the `request:<id>` hash with one `task:<tid>` field per task). Proposed on Day 3 in `docs/messages.md` and approved by Person B. | The design doc names these keys without defining them, and both the API and atsd depend on them. One field per task lets atsd update a single task with one `HSET`. Keeping the plan in a separate API-owned key means status works before atsd runs, and atsd's hash holds only runtime state. |
| D26 | **`minisched`: a Python stand-in for atsd, for testing only.** FIFO dispatch, no retries, no deadlines; writes the D25 status hash. | Lets the worker and API side (and the Day 3 three-worker rehearsal) run end to end before the C++ atsd exists. It is a test tool, not a second scheduler, and must never run alongside atsd because both would consume `requests:new`. |
| D27 | **LLM executor** (now `worker/worker/executors/llm.py`, async via `AsyncGroq`)**:** one Groq call per attempt, no SDK retries.** `LLMExecutor` uses `ATS_EXECUTOR_MODEL` (default `openai/gpt-oss-120b`), `max_retries=0`, and a request timeout equal to the time left before `deadline_ms`; it refuses to call once the deadline has passed. Dependency results go into the user message in task-number order. | Retries and back-off belong to atsd (8.6), which sees the attempt history; SDK retries would hide failures and overrun the deadline atsd owns (8.7). |
| D28 | **Sim expand returns a canned 2-task Subplan.** `SimExecutor` answers an expand task with `s1…sN` research tasks (N = 2), `result_kind: "subplan"`. A plan's `hints.sim_subplan` is not used, because `TaskMessage` doesn't carry it. | Lets atsd's splice path be exercised on `tasks:sim` without an LLM. If atsd should splice the fixture's own subplan, contract #2 needs a field for it. |
| D29 | **Worker order of operations** (superseded on Day 3 by D31). Publish `task_started`; skip with retryable `task_failed` if `deadline_ms` has passed; if the result key already exists, report `task_completed` with `committed: false` without re-running; otherwise read inputs (missing → retryable), execute, `SET NX`, report. XACK is always the last step, and entries idle for more than 30 s (`--claim-idle-ms`) are taken over with XAUTOCLAIM. An unparseable message gets a permanent `task_failed` when its `attempt_id` can be recovered and is otherwise acknowledged and dropped. | A crash at any point leaves the entry pending, so another worker finishes it, and the write-once key makes the re-run safe: an attempt may run twice, a result is recorded once (8.5). **Resolved:** `worker/` was kept (D31). Its skip-if-result-exists and skip-if-deadline-passed checks moved into `worker/`; the XAUTOCLAIM takeover was dropped because D10 (revised) makes atsd's deadline the only lost-attempt detector; a missing input stays permanent (D24). |
| D30 | **Result values are JSON** (revised from "stored verbatim"). An output is stored as `{"content": <text>, ...}`; an expand task's result is the Subplan JSON. `result_kind` is derived from the task type (expand → `subplan`), so a duplicate report needs no extra key. Keys have no TTL. Readers treat a non-JSON value as plain text. | Design doc 8.9 specifies JSON output (`{content, key_points, sources?}`). Plain text broke the API's status endpoint and `worker/`'s input loading, so the two workers could not share results. Expiry is a request-lifecycle decision for atsd. |
| D31 | **One worker: `worker/`.** `planner/planner/worker.py`, `devrun.py` and `executors.py` were removed on Day 3. The Groq executor, its prompt, error classification and the sim expand subplan moved into `worker/` (D27, D28); the planner package no longer depends on Redis. | `worker/` follows D10 (no XAUTOCLAIM) and is the one Docker and the API are built around. Two workers had diverged on result format, missing-input handling and sim durations; one implementation removes that class of bug. |
| D32 | **atsd talks to Redis through hiredis directly**, behind a small `Bus` interface (`RedisBus`), not redis-plus-plus. | Design doc 12.7's fallback. hiredis is one C library, available from Homebrew and Debian, so atsd builds on macOS, in CI and in a slim Docker image without compiling redis-plus-plus. The `Bus` interface lets the service logic run against a fake in unit tests (10.3). |
| D33 | **atsd dispatch and retry rules.** Requests are served least-recently-served first (a new request first), the policy picks within a request. Capability caps count attempts in flight; a request is only asked for a task while every capability it uses has room (exact with one capability per request, conservative otherwise). A failed or lost attempt frees its slot at once; during the backoff the task stays QUEUED/RUNNING in `ExecutionState` (shown as RETRYING in `request:<id>`) so a late committed result still completes it; one arriving after the task re-entered the ready set completes it on its next dispatch without sending a message. Every task goes to `ATSD_CAPABILITY` (sim in docker-compose, llm by default). | Keeps the state machine unchanged while honouring 8.5 step 7 (late results are valid). Least-recently-served is a simple stand-in for FairShare (Day 4). |
| D34 | **Expand results are not spliced yet.** A `task_completed` with `result_kind: "subplan"` completes the expand task like any output and is logged as `subplan_not_spliced`. | Splicing (8.11) is Day 6; until then a plan with an expand task still runs to completion. |
